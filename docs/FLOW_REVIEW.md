# jrxy_auto_cf 流程审查

## 范围与结论

审查覆盖：管理员登录、账号存储、CAS/IAP无验证码登录、任务查询与选择、表单、设备ID、动态密钥、签名提交、复查、每日计划、批量顺序、暂停/恢复、通知、日志、数据迁移与部署。

基线为所附 Python 原项目的实际 Web 调用链：`web-server/app.py` → `jrxy-engine/scripts/merged_ios_v4_submit.py --variant fkey_cat --protocol ios`，而不是 README 中未被当前入口调用的所有历史功能。

**主协议和对应业务规则按原实现保留，并使用原Python生成的合成样本对照。运行架构、登录管理、暂停、安全处理和异步API存在明确变化，因此不能宣称每条旧代码或所有异常行为完全相同。** 真实学校、远程免费CPU配额及通知终端送达不在本地验证结论内。

## 本次审查修复

### 一分钟普通请求等待与有效参数展示

- 默认普通学校请求等待从30秒改为60秒，`settings`和直接`Session`共享默认值；队列、登录测试、用户授权统一生效。显式环境值仍优先，单账号300秒网络总时限和执行位租约不变，密钥协商/签到提交20秒与通知15秒不变。
- 受控时钟验证45秒返回的门户GET、登录POST和回跳POST在60秒内可完成，显式30秒仍超时；超过60秒或累计达到300秒仍停止，晚到响应丢弃且不污染Cookie、不重复发送POST。
- 管理员状态及执行设置显示实际请求/总时限/提交参数，不靠文档推断部署是否生效。新执行读取新参数，不复活已耗尽任务。
- 结构化诊断与业务文本分开：先脱敏消息和详情，再通过白名单校验并生成诊断行。修复短隐私值碰巧匹配固定阶段名时把`login_callback`误改的问题；域名仍脱敏，不记录URL、票据、正文或Cookie。
- 加时只检验慢响应假设，不足以证明现场根因。原Python回跳同样POST、默认读超时30秒；本机原生报文对照空POST两者均Content-Length 0，但Cloudflare出口/TLS和平台自动头与VPS不等价，不宣称完全相同。

### 门户520与手动批量接续

- `portal/http/520`表示门户跳转阶段收到了上游HTTP错误，尚未提交签到；仅凭此诊断不能认定由部署更新导致。仍按暂时上游错误进入整轮有限重试，不通过增大并发或绕过限流处理。
- 已复现多个账号等待重试时，“签到全部”返回空列表且笼统提示忙碌的缺口。`admitJobs`在同一事务内建空闲任务、接续已有任务、清空批次并返回分类，单账号和批量共用，重复并发调用不会重复建任务。
- 同一未结束批次的成功账号只展示既有结果。返回新增/接续/已成功及暂停、其他操作占用、到期失效数量；前端展示原进度，不重置次数、等待时间或提交检查点。
- 门户520模拟覆盖：首轮提交前失败、整轮结束后等待5分钟、手动接续不提前重试、下一轮串行恢复成功、先前成功账号不重签。样本不包含现场学校域名或个人日志。
- 页面重复打开同一任务时保留全部完成回调，避免先前按钮一直等待；轮询、最早执行时间和降级原因保持。

### 成功即停止与发布前兜底审查

- 逐段复核账号/设备准备、CAS/IAP登录、任务列表与表单、密钥协商、提交保护、明确成功或同目标复查、结果落盘、报告通知和下一轮调度。保留原成功路径请求轨迹，不对已经明确成功的请求增加反复确认。
- 1/2/3并发首次成功账号仅登录/提交一次；重复投递、后续Cron、其他账号重试均不重新执行。只停止本次任务，次日计划仍可建立新任务。
- 成功结果先持久化；通知503、日志事务失败不改写签到成功、不再次提交。结果事务失败仍保留提交检查点，恢复只复查原任务。
- 新增故障复现：通知服务忽略abort、正文或cancel挂起，原实现会拖住报告。复用HTTP截止时间与取消工具，将通知整体限制在15秒；超限不等待无限cancel，迟到响应丢弃，记录通知失败但保留签到结果。
- 新增故障复现：提交前目标/检查点D1写入失败被引擎捕获后可能变成最终执行失败。现在单独标记持久化故障并交给队列/Cron有限恢复，不当成学校拒绝，也不会在检查点写入失败后发送提交。
- 根README精简，复杂部署与排障保留在部署手册；明确构建环境注入D1 ID、三个运行时Secret、增量迁移和沿用ENCRYPTION_KEY，不发布真实部署标识。

### 整轮重试、提交证据与队列恢复

- 原 `_fire()` 默认额外重试2次，本轮按要求改为5次。`generate-scheduler-fixtures.py` 仅AST提取原函数，禁用网络，以合成结果生成恢复成功/预算耗尽两组轨迹；对照串行账号顺序、10秒间隔、整轮结束后5分钟等待和成功账号不重跑。
- 提交及复查都超时不再直接丢弃后续机会：目标与提交检查点持久化，未知只复查同一signInstanceWid；明确未签才清除提交检查点、保留目标用于后续执行。最终未知仍是待确认。
- 任务列表缺必要字段、业务错误带空数组都不能记为无任务。“重复请求/尚未签到/处理中”等文本不能证明已签或解除提交保护；明确成功或同任务已签证据才算成功。可信空列表保留无任务并注明不是成功。
- 手动入口复用在途签到的任务ID；后续手动/定时在实际领取账号锁后读取最新未决证据，避免建批快照过旧。删除换号不继承旧账号证据；未决期间不能更换学校/身份/任务类型，但可纠正密码。
- 每条派发具有投递标识，提前到达延迟重投；旧/重复消息及迟到的发送失败不能释放新预留。日志、通知状态与报告完成均核验租约及执行位，报告恢复不重签。
- 并发1/2/3经实际Queue消费者与完整模拟登录/任务/加密链路测试；明确网络暂时错误只将下一重试轮降为串行，全局设置不变。418/429停止请求，绝不通过加大并发或盲目重试规避。
- 连续进程中断恢复与业务轮次分开计数，完成结果后重置中断计数；空历史批次可结束，次日计划能继续。未知旧目标跨日仍只复查，若学校当日接口不再返回旧目标，需要人工核实，不能自动假设已签或未签。
- 后台显示真实轮次、剩余机会、最早执行时间、仅复查和降级原因；“已结束”不等于成功。HTTP毫秒级单元测试采用受控时钟，原生fetch检查仍用真实计时和本地网络出口。
- 未取得现场失败日志，无法把用户某次2并发失败归因于并发。无论串行还是并行，都不能保证学校永不超时；需要结合安全诊断、官方任务窗口和Cloudflare Metrics核实。

### 登录请求逐节点与读取超时复核

- 核对学校列表→租户详情→门户跳转→登录页或IAP票据→验证码检查→提交→回跳。CAS/IAP既有参数、请求顺序、跳转、固定设备ID处理保持不变；每次授权创建独立的Session，排队等待不消耗HTTP等待预算。
- 旧版把等待响应和下载正文合计限制在同一个30秒窗口。合成慢流持续返回数据但超过该窗口时，旧版可复现误超时。现在从响应头开始按无进展计时，收到非空分块重置，仍受会话网络总时限、大小和跳转上限约束。
- 首次响应迟到、正文卡住、总时限用完分别验证；取消被卡的流，忽略逾期响应及其Cookie。不自动重放登录请求。模拟同校三账号成功→超时→成功，Cookie隔离，失败凭据清理、执行位释放，失败码保持可用。
- 管理员诊断增加请求序号、跳转次数、等待阈值、无进展时间、已读字节数及会话耗时，不返回个人数据或原始请求内容。成功与超时的真实差异仍需线上那一条脱敏诊断确认；本地复现不能判定线上根因。

### 授权管理、通知与有限并发

- 新授权码摘要＋独立上下文AES-GCM密文，未使用可再次复制，使用/撤销/过期清理密文；旧摘要码无法恢复但不作废。每页10条，跨页操作标明整批数量，整批撤销不影响已用账号。
- 默认24小时从激活起算，旧期限不变。用户可选SCT SendKey，默认关闭；拒绝网址注入、加密保存、幂等包含Key、失败/撤销/到期清理，保留原通知调用规则。
- 权重0～100，只由管理员设置并在建批时快照。并发默认1、最高3，D1执行位+账号锁+原全局门闩兼容保护；按权重同组并行，组间保留间隔，整轮后重试。
- 在途授权即使回执过期仍保留其执行容量租约直到返回/任务总时限，不能因清理临时记录而让另一请求超额并行。提交/结果回写再次校验执行位owner及租约。
- Queue单消息处理，不用Promise.all把多账号堆在单次Worker中；本地模拟6任务每个150ms等待，1/2/3并发约1.13/0.66/0.51秒，全部完成。只是模拟等待提速，非远程CPU或学校容量保证。
- Cron每次只清理1个过期账号、1个失效验证并最多补发1个验证，优先控制单次查询工作量；过期资格在执行入口即时拦截，不依赖清理完成。

### 原生fetch调用错误复核

发现并在真正的workerd中复现一个确定性阻断：`Session`将原生fetch保存为成员后用 `this.transport(...)` 调用，接收者变成Session对象，原生函数抛出 `Illegal invocation`。在到达网络出口前就失败，旧异常包装却显示为DNS/TLS/连接问题。

- 修复为先取出函数，再以普通函数调用，避免错误this；不更改账号、设备ID或协议参数。
- 明确的Illegal invocation归为内部调用错误、不重试，不输出原始异常或其中的敏感字段。
- 之前158项（含原Python请求轨迹）使用替代fetch，不能发现原生函数接收者限制。新增 `scripts/test-native-fetch.mjs` 保留真正的workerd原生fetch，只将网络出口转给本地内存服务。
- 同一测试修复前失败、修复后通过22项检查/246次本地请求：默认/显式fetch注入、16条原入口链路、4条自助开通使用的直接登录链路。姓名与学校用户名设置为不同值，检查上游仍使用用户名。
- `npm test`已强制串联该原生测试。此证据确认代码阻断已修复，不等于真实Cloudflare出口与学校证书/服务已验证。

### 请求轨迹复核

此前133项通过覆盖业务规则与模拟流程，未证明完整HTTP请求链路一致。本轮先从原Python入口捕获16条合成轨迹，修复前16条均不匹配，修复后全部通过：

- 原 `test_login.py` / `fetch_sign_range.py` 一轮学校发现；原 `merged_ios_v4_submit.py` 调用发现两次，登录后还查询一次租户。Worker已恢复这些顺序，不再用学校元数据缓存跳过请求。
- CAS发现登录地址后再次GET登录页，使用最新Cookie、execution和密码盐；`casLoginForm`整页字段与其他模板的限定范围分开处理。
- 表单使用Python urlencode规则（包括`~`、`*`等字符）、登录AES串按原76列换行；IAP的`{}`正文不擅自添加JSON或text/plain类型。
- 请求JSON的空格及ASCII转义匹配原调用方式；动态密钥和提交按原显式20秒请求时限；原段值非空检查保留。Workers整体计时语义仍不同于requests读超时，见下文。
- 空Cookie头不发送；标准getSetCookie和Workers getAll兼容，多个Cookie及Expires逗号不合并拆错。响应头/正文处理异常不再伪装成连接失败。
- `original-http.test.ts` 比较16条轨迹的应用层方法、URL、显式请求头、正文和Cookie。固定随机输入后对齐签名及加密头；RSA随机填充只校验结构，不逐字比较。另测同学校不同账号不共享Cookie或跳过发现。

轨迹生成只执行AST提取的原函数，requests使用内存适配器且socket连接被禁用；不导入原Web服务器、不读取账号目录。传输层自动添加的Content-Length、压缩/连接头以及TLS握手不在逐字对照范围内。

### 既有审查修复

- 重复 `loginFromId` 表单不再把不同表单隐藏字段混在一起，选取与原模板对应的第二个。
- IAP跳回登录页时不再仅凭预登录Cookie误报成功。
- 查询验证码状态遇到异常HTTP响应时停止，不盲目提交密码。
- 任务列表结构异常、范围无任务及坐标无效时返回明确失败，不进入提交。
- 范围结果补回 `signWid`，保持原查询结果契约。
- 重试结果已落盘、通知/日志尚未完成时发生暂停或恢复，恢复报告阶段会终止旧重试，不继续运行或伪报失败推送。

## 必须保留的差异与边界

1. Python常驻线程/子进程/本地磁盘改为Workers、Queues与D1，这是平台迁移，不是原代码原样运行。
2. 管理账号密码登录与账号暂停为明确新增要求。
3. 后台和兑换账号统一按原Web `ensure_device_id()` 规则，登录/探测前先沿用可确认绑定，无值时首次生成UUID并固定。管理员可选填旧ID，编辑留空保持原值。原独立 `test_login.py` 仅做CAS/IAP登录，ID参与后续动态密钥协商和签到；不为登录接口臆造设备字段，也不能凭生成ID保证学校设备授权。
4. 不使用OCR，不上传照片，不提供类型0/3/4任务；触发验证码停止并报告。
5. 仅支持公网HTTPS和有效TLS证书，不照搬 `verify=False`；本机HTTP代理不适用于云端。
6. 原requests默认连接10秒、读取无进展30秒，协商与提交显式20秒。Workers普通请求按新要求改为60秒，协商与提交仍显式20秒，分别约束等待首次响应头和正文无进展；保留默认300秒会话总时限、大小和跳转上限；不能观察单独的TCP连接时刻或每个到达的网络字节。不对送达情况不明的fetch异常重放POST；免费配额及出口/TLS差异仍需远程Metrics和同次脱敏诊断核实。
7. 外部推送没有端到端幂等键，发送期间崩溃可能未知；不会把未知写成成功。
8. 运行API异步返回任务ID，页面内部轮询；直接调用旧同步API的脚本需要适配。
9. 新安装尚无授权时定时默认关闭；首次成功兑换可开启未由管理员设置过的初始计划。主动关闭/保存过的计划不覆盖，兑换账号只参与开通后的计划，不立即签到或补跑。
10. 日志脱敏，不照搬原代码打印会话令牌、密码或密钥的调试输出。
